# Equipment/Crafting 2.0 — source issuance and atomic craft boundary V4
**22 Nov 2026 · private review-only implementation · not activated or deployed**

## Implemented in the hidden GitHub branch

- **14 required material source definitions** in `backend/src/server/equipment/equipment-crafting-v2-material-source-review.ts`. The records encode T1–T4 material IDs, existing candidate monster IDs where grounded, tier-entry risks and gathering-route needs. Every record has `isRegistered:false`, `grantVerified:false`, `mintAuthorized:false` and `releaseEnabled:false`; `preflightEq2MaterialGrant` always refuses granting, including when passed claimed verification.
- **746-route non-executable reservation preview** in `equipment-crafting-v2-unified-reservation-review.ts`: loads only a server-supplied reviewed recipe, checks its distinct foundation/alternate pair, common/scarce/binder parity, finite positive costs, only same-profession crafting gate, authenticated account/character identity *as presented by a future trusted adapter*, stale account revision, owned Inventory+Bank balances, Gold, duplicate request IDs and existing receipt replay. It never mutates input objects and always returns `allowedToCommit:false`.
- Existing hidden `equipment-crafting-v2-transaction.ts` no longer treats the legacy recipe's `characterLevel` as a crafting prerequisite. An independent specialist can craft by **Smithing or Tailoring** proficiency and material ownership, without leveling Combat. Equipping combat gear remains an independent tier/class eligibility problem. A low-combat, sufficient-profession test was added. Nothing changes the 1.0.x live app.
- Dedicated `tools/test-eq2-material-source-and-reservation-v4.mjs` tests all 14 source records against the v3 recipe input requirements, compiles the isolated server-only modules, quotes all 746 recipes with item-by-item Bank splits, and exercises account spoofing, revision mismatch, Gold/material exhaustion, invalid quantities, forged alternative routes, duplicated receipts and replay.
- The hidden CI workflow enforces isolated strict TypeScript and rejects imports of these unissued source/reservation functions into public/mobile/Edge entrypoints.

## Real backend availability: blocked, not shipped

No 2.0 source is registered in staging. The previously verified staging PG17.6 snapshot had 0 Equipment 2.0 processing definitions, EQ2 resource bindings, 2.0 craft receipts/jobs and `EQ2_LAUNCH_%` copies in the specifically inspected tables. This authoring pass performs **no SQL, live loot table registration, Edge function route, production data, or actual owned material/item writes**. Existing server `equipment-crafting-v2-server-projection.ts` intentionally rejects `EQ2_`-prefixed stack keys, to avoid disguising unique equipment copies as materials. **Do not relax that blanket guard until a server-owned, strictly item-type-checked stackable-material registry and real source/receipt proofs replace it.** The v3 currently proposes new `EQ2_` material IDs; these are not yet legitimate live inventory stacks.

## Mandatory real issuance/commit architecture

1. **Trusted material registry:** register each new material ID with authoritative identity, stackability, source, tier, expected quantity, rarity, unlock conditions and allowed market transport; allowlist material IDs only after verified source ownership. Existing `IRONWOOD_FANG` remains one identity and uses its existing payout/Alchemy; no duplicate roll. Existing `SUNSTONE_INGOT` remains one canonical processing recipe, not a second double-XP source.
2. **Server-generated source proof:** monster drops require exact monster instance/eligible kill, source tag and original event receipt; processing requires a versioned input-reservation receipt; gathering needs source node ownership and cooldown. Client may select activities, but may not choose item grants, chances, RNG seed or quantities. Reject dupes, invalid source level and unowned accounts.
3. **Single atomic account commit:** independently authenticate via session and lock the account revision, active character/owner, wallet, shared Bank, queue, item registry and idempotency receipt, using one account-scoped serializable transaction. Preserve legacy owned equipment/gem/copies, existing Bank/item accounting and exact parent receipt. Any failed step rolls back all Gold and resources; queue jobs snapshot validated recipe version and material cost.
4. **Idempotent claim:** a queued job can be claimed exactly once after authoritative finish time. Deterministic source-bound rarity/quality/affix mint grants a unique owned instance; XP accrues to the original crafting character once; repeat requests return the stored result without another credit. No material stack can masquerade as an equipment copy; copies, gem sockets, sell/salvage locks and account/multi-character storage require parity.
5. **Market/commissions:** combat-origin components may be transferred in future via authenticated escrow/commission receipts, so noncombat crafters can advance to T9 without leveling combat or unrelated gathering skills. Ordinary crafted gear may be marketable only under a future approved policy; exclusive dungeon, party or boss equipment cannot be crafted/market-listed by accident.
6. **Staging authorization:** only after owner approval of final item identities/material rates and canonical recipe contracts, run **migration with rollback plan** on staging; verify two concurrent connections, replay, order cancellation, source payout normalization, level-2 Boar gap, T3 level-26 rare bridge, Sunscar hide species, T4 profession-accessible Glassbound Dust and 9-class/18-spec combat tests. UI/theme/art go through explicit design acceptance before any runtime UI changes.

Successful isolated TypeScript and synthetic preview QA supports code-contract correctness only, not actual live supply, rarity drops, market custody, payout security or production readiness. Existing legacy mobile/Edge CI failures on this stacked branch need separate reconciliation; don't treat them as equipment-v4 test results.
