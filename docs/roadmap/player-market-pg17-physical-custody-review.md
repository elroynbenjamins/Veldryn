# Market review — PostgreSQL settlement and physical custody
26 November 2026. HIDDEN review only. No Supabase migration, production/staging connection, actual wallets/items, release flag, UI or route changes.

## PostgreSQL
A standalone PostgreSQL 17 CI service runs tools/market-review/pg17. Dedicated database and role eq2_market_review, disposable session marker, localhost runner, no deployment credentials. The model uses a unique original mint and single custody row per copy, append-only sale/request history, one active offer per instance, atomic wallet debits/credits, ceil(5%) fee and ordered wallet locks after per-copy and policy locks. All receipts explicitly deny Market authority. Rollback regressions cover bank deposit/withdraw, eligible same-account alternative character, full capacity, invalid recipient, replay conflicts, first and subsequent sales, expiry, revoked policy and immutable original mint. Two separate clients contend for one listed copy and for cancellation versus purchase; the winner holds a row lock before contenders start. Assertions check one sale, exact Gold balances and recoverable pending custody. CI outcome must be verified before counting any SQL or race as passed.

## Physical inventory / bank
28 synthetic coverage checks passed in JS isolate. Full account snapshot requires inventory, pouch and equipment for every known character, plus shared bank; rejects omitted/duplicate stores, duplicate copy, stale revision, wrong account, wrong location, wrong original/current digest, equipped/locked/favorite/saved/protected gear. Bank-held items must be withdrawn before listing in this review. Escrow and pending entitlements require no physical inventory copy and a matching entitlement identity; they cannot be listed. Original mint digest and current authorized mutation digest are separate. Fixture does not independently verify source truth or entitlement, and never authorizes Market.

The SQL model represents physical ownership as a single normalized custody row, not actual GameState JSON or original Forge serialization. The V32 source audit identified that the existing Forge readback projection uses virtual locations and false protection flags. The eventual adapter must derive complete real account roster, stores, capacities, protection status and authorized socket history from locked DB state, compare global physical identity and custody, perform authoritative character progression/recipient checks and persist all wallet/custody/game-state revisions and receipts atomically. No client-supplied fixture values are trusted. Use a single compatible lock ordering across real gameplay paths; recheck current source policies, account and character row versions. The current review assumes dedicated fixtures, account-level inventory capacity and simple eligibility boolean; real per-store capacity, actual bank/character rules, upgrades, protected returns, authenticated worker and cross-source issuance remain unimplemented. Current SQL races do not cover all lock interactions, multi-item transactions or crash recovery. No new listing cap, pricing, tax, expiry or VIP rules adopted.
