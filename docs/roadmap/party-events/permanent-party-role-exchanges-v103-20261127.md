# Permanent Party role exchanges — 2.0 hidden review
Owner approved 27 November 2026. This is a general persistent Party feature, not a dungeon or Party Event feature.

## Rules
Each account has at most one owned character per role. No unilateral registered role change; all changed accounts participate in a consented two-way exchange or three-/four-member coordinated rotation. Every changed account selects its own character of the new role. Preserve the exact existing role multiset (including incomplete Parties); the full existing 1 Tank / 2 Damage / 1 Support distribution is not relaxed. No new class restriction is imposed by this Party-level exchange. Every replacement must meet the existing Party minimum level and current ownership/class checks. Party ID, membership rows, leader, name, contract contributions, rankings and chat remain intact. Global active-character selection is separate and must not automatically change registered Party roles.

## Transaction contract (not implemented)
1. Authenticated proposer is an active member; canonical server creates immutable proposal ID bound to party, exact before/after member selections, revision and expiry. Participants independently consent to their own target on that exact proposal. Decline/cancel/expiry closes the proposal; no partial change.
2. On final confirmation lock party and all active membership/ownership rows, re-read exact revision, account membership, current roles, class and combat level from canonical character sources, minimum level and pending consent rows; use reviewPartyCharacterSwapV103 in persistent_party mode as a non-authorizing projection. Any stale proposal, membership/ownership change or incompatible activity lock fails closed. Never accept arbitrary client-owned character/consent lists.
3. Commit all changed registrations in one database transaction, preserving stable membership IDs, joined timestamps, leader and activity history; increment roster revision once; invalidate only uncommitted readiness/loadout caches. Account ownership and immutable old encounters remain unchanged. Do not silently rewrite old contract or event contribution character IDs or reward recipient snapshots. Existing activities may continue with their frozen roster where safe; no in-flight actor replacement. A global active-character change is not a swap.
4. Receipt keyed by immutable proposal, account and party; duplicate final confirmations recover the same result rather than another mutation. Need independent multi-session tests for simultaneous conflicting proposals, duplicate confirmation, disconnect, stale revision, departure/deletion, partial failure and lost acknowledgement. Check database role-slot uniqueness and safe atomic update strategy rather than temporarily deleting/rejoining membership rows.
5. Refresh party member character/class/role projections on success; recompute Class Synchronization on subsequent new encounter from the registered heroes. No transfer of character gear, level or skills.

## Further interaction ideas — recommendations only, not approved for implementation

- Party Event route/preparation votes: use existing authoritative event voting window, not a second competing vote mechanism.
- Group readiness check: ready/not ready for a planned group activity; preserve actual dungeon ready-check authority.
- Invitation and join request: permitted recipient actions, leader approval only where already required; no public exposure of private invite cards.
- Shared milestone notifications: passive contract completions, upcoming expiry and Party Event milestones; deduplicate and avoid chat spam.
Keep the first four structured actions within their owning workflows; no cross-channel automatic acceptance, resource spending, reward claims or leader changes through arbitrary chat text.
